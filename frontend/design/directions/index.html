How does it support rotating to a new secret key while old keys still work?

The library supports key rotation by accepting an iterable of secret keys and storing them as a list ordered from oldest to newest.

  1. Key storage. Both Signer and Serializer accept secret_key as a string, bytes, or an iterable. The helper _make_keys_list converts it into a list[bytes] stored in self.secret_keys1. The documentation says the list is ordered “from oldest to newest” and that the “newest (last) key is used for signing”2.
  2. Signing. Signing uses the last item in secret_keys. The secret_key property returns self.secret_keys[-1]3, and derive_key also defaults to it when no key is given4.
  3. Verification. verify_signature walks self.secret_keys in reverse, newest to oldest, and accepts the signature as soon as one key verifies it5. Tokens signed with an older key stay valid while that key is in the list.
  4. Serializers. Serializer stores secret_keys the same way and exposes the same secret_key property67.

To rotate, add the new key to the end of the list. Keep old keys until no tokens signed with them can still arrive, then remove them.
